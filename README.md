# WHOI Marina Reservation System (prototype)

Berth reservation system for the marine research facility's waterfront: vessel and non-vessel
(community events, tours, maintenance) reservations, a dock-schedule calendar view, automatic
overlap/conflict detection, and an import of the 1997–2019 historical spreadsheet.

**Read [`ISSUES.md`](ISSUES.md) before trusting the imported historical data operationally** — it
documents every ambiguous decision the importer made and the bugs found and fixed along the way.

## Stack

- **Backend:** Java 21, Spring Boot 3, Maven
- **Storage:** JSON flat files in `data/` (no database — see `ISSUES.md` §8 for what that does and
  doesn't guarantee)
- **Frontend:** static HTML/CSS/vanilla JS, served by the Spring Boot app (no separate build step)

## Running locally

Requires a JDK 21 on `PATH` (`JAVA_HOME` set) and Maven. If this machine was set up during the
original build session, both are already installed:
- JDK: `C:\Program Files\Eclipse Adoptium\jdk-21.0.12.101-hotspot`
- Maven: `C:\tools\apache-maven-3.9.9` (added to your user PATH)

```bash
mvn spring-boot:run
```

Then open http://localhost:8080. On first run (empty `data/` directory), the app automatically
imports `Dock Schedule - Synthetic Sample.xlsx` from the project root — this can take a few
seconds and only happens once; subsequent restarts skip it. To force a clean re-import, either
delete everything under `data/` or set `MARINA_FORCE_REIMPORT=true`.

### Configuration (environment variables)

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `8080` | HTTP port |
| `MARINA_DATA_DIR` | `./data` | Where the JSON store files live |
| `MARINA_SOURCE_XLSX` | `./Dock Schedule - Synthetic Sample.xlsx` | Workbook to import on first run |
| `MARINA_FORCE_REIMPORT` | `false` | Re-run the import even if data already exists |

## Running the tests

```bash
mvn test
```

23 tests covering the validation engine's scheduling rules (overlap detection, rafting
downgrades, LOA/berth-fit, missing-data flags), the JSON store's atomicity/concurrency
guarantees, the spreadsheet grid parser (including a regression test for the bare-month-title
bug described in `ISSUES.md`), and recurring-reservation expansion.

## Project layout

```

  store/       JsonCollectionStore — the atomic, lock-protected JSON flat-file layer

  importer/    the one-time historical spreadsheet import pipeline
  web/         REST controllers
  config/      Spring configuration / bean wiring
src/main/resources/
  application.yml
  static/      the frontend (calendar, reservations, vessels, berths, dashboard, review queue)
src/test/java/...
data/          JSON flat-file "database" (git-ignored; regenerated by the importer)
```

## API surface (selected)

- `GET/POST /api/reservations`, `PUT/DELETE /api/reservations/{id}`, `POST .../cancel`,
  `POST /api/reservations/series` (recurring)
- `GET/POST/PUT/DELETE /api/vessels` (search via `?q=`)
- `GET/POST/PUT/DELETE /api/berths`
- `GET /api/availability/suggest?start=&end=&loaFt=` — "find an available berth"
- `GET /api/dashboard`
- `GET /api/validation-flags`, `POST /api/validation-flags/{id}/resolve`
- `GET /api/import/review-queue`, `POST /api/import/review-queue/{id}/resolve`
- `GET /api/export/reservations.csv` (same filters as the search endpoint)

All mutating endpoints accept an `X-User` header (defaults to `"staff"`) for the audit log, and
reservation creation accepts an `Idempotency-Key` header to make accidental double-submits safe.

## Deployment

A `Dockerfile` and `render.yaml` are included and ready to use, but **nothing has been pushed to
a public repository or deployed anywhere yet** — that's a deliberate pause point, not an
oversight. To actually go live:

1. `git init` has already been run locally with an initial commit. Create a GitHub repo and
   `git remote add origin <url> && git push -u origin main` when you're ready to make it public.
2. On [Render](https://render.com): New → Blueprint → point at the pushed repo → it will pick up
   `render.yaml` automatically (builds the Docker image, sets `PORT`, persists `data/` on a disk).
3. The `Dockerfile` copies the source `.xlsx` into the image so a fresh deploy can self-seed; if
   you'd rather ship it pre-imported, mount a volume with an already-populated `data/` directory
   instead.
